Exam format (DVA-C02)
  • 65 questions (50 scored + 15 unscored), 130 minutes, about 2 min per question
  • Multiple choice (1 of 4) and multiple response (select exactly N of 5+)
  • Scaled score 100-1000, pass = 720
  • Domains: Development 32%, Security 26%, Deployment 24%, Troubleshooting and Optimization 18%
Strategy
  • Read the last sentence first: what is actually asked (cheapest? least operational overhead? fastest?)
  • Eliminate 2 wrong options, pick between the other 2
  • Flag hard questions and come back, never leave blanks
  • "Serverless" and "least operational overhead" usually point to managed services
Keyword to service
  • reduce read latency: DAX (DynamoDB), ElastiCache, CloudFront, API Gateway cache
  • decouple / buffer: SQS; fan-out: SNS; ordering: SQS FIFO or Kinesis
  • replay events / many consumers: Kinesis Data Streams
  • secrets with rotation: Secrets Manager; config values: Parameter Store
  • feature flags / gradual config rollout: AppConfig
  • temporary AWS credentials for app users: Cognito Identity Pool, STS
  • who called which API: CloudTrail; metrics and logs: CloudWatch; trace requests: X-Ray
  • encrypt large data: envelope encryption (GenerateDataKey)
  • cross-account access: IAM role plus trust policy (and resource policy)
  • zero-downtime deployment: Beanstalk Immutable / Blue-Green, CodeDeploy blue/green, Lambda aliases

IAM basics

At a glance

How IAM decides (evaluation logic)

  1. 1Start with implicit deny
  2. 2Any explicit Deny? then DENY
  3. 3SCP / permissions boundary must allow
  4. 4Identity or resource policy has an Allow? then ALLOW
  5. 5Otherwise DENY

Policy types

TypeAttached toEffect
Identity-baseduser, group, rolegrants permissions
Resource-basedS3, SQS, SNS, Lambda, KMS (has Principal)grants access to the resource, also cross-account
Permissions boundaryone user or rolemaximum permissions (never grants)
SCPaccount or OU in Organizationsmaximum permissions for the whole account
Session policyan assumed-role sessionfurther limits that session
Exam traps
  • An explicit Deny always wins.
  • Cross-account access needs permission on both sides (or an assumed role).
  • Use roles for applications, never long-term keys.
  • A permissions boundary never grants permissions by itself.
Details

IAM, CLI and SDK basics

IAM
  • Users, groups, roles, policies. Root account: lock away, enable MFA, do not use daily
  • Policy JSON: Effect, Action, Resource, Condition (and Principal for resource-based policies)
  • Evaluation: explicit Deny always wins, otherwise needs an explicit Allow, default is deny
  • Roles give temporary credentials (via STS): use them for EC2, Lambda, ECS, cross-account
  • Identity-based policy (attached to user/role) vs resource-based policy (S3 bucket, SQS, Lambda, KMS key)
  • Least privilege: scope actions and resources, use conditions (aws:SourceIp, aws:RequestedRegion, aws:MultiFactorAuthPresent)
  • IAM Access Analyzer finds resources shared outside the account; credentials report shows key age
CLI and SDK
  • Credential chain order: command-line flags, environment variables, CLI profile files, container credentials, EC2 instance profile
  • If no region is set the SDK defaults to us-east-1
  • Never put keys in code. On EC2 use an instance role
  • Throttling (429) and 5xx: SDK retries with exponential backoff and jitter automatically
  • Requests are signed with Signature V4 (SigV4)
  • aws sts decode-authorization-message decodes the encoded AccessDenied message
  • IMDS: http://169.254.169.254/latest/meta-data/, use IMDSv2 (token first, then GET)
  • --dry-run checks permissions without acting; --query (JMESPath) filters output; --profile picks a profile

IAM policies in depth

Policy document
  • Version, then Statement list. Each statement: Effect (Allow/Deny), Action (or NotAction), Resource (or NotResource), optional Condition, and Principal only in resource-based policies
  • ARN format: arn:aws:service:region:account-id:resource. S3 object ARN: arn:aws:s3:::bucket/key; bucket ARN has no key. s3:ListBucket applies to the bucket ARN, s3:GetObject to bucket/*
Types
  • AWS managed policies (maintained by AWS), customer managed policies (reusable), inline policies (embedded in one identity)
  • Identity-based (user, group, role) vs resource-based (S3, SQS, SNS, Lambda, KMS, Secrets Manager; has Principal)
  • Permissions boundary (limits max permissions of one identity), SCP (limits whole accounts/OUs), session policy (limits an assumed-role session)
Evaluation logic
  1. Start with implicit deny
  2. Any explicit Deny in any applicable policy: denied
  3. SCP and permissions boundary must also allow (if they exist)
  4. Otherwise an Allow in identity-based or resource-based policy grants access (same account: either one is enough; cross-account: both sides must allow)

Conditions: StringEquals, StringLike, IpAddress, Bool, DateLessThan, ArnLike; keys aws:SourceIp, aws:RequestedRegion, aws:MultiFactorAuthPresent, aws:PrincipalTag, aws:SecureTransport, aws:PrincipalOrgID. Policy variables: ${aws:username}, ${aws:userid}. Add IfExists when the key may be missing.

Roles and trust
  • A role has a trust policy (who can assume it) and permission policies (what it can do). Service roles (Lambda execution role, ECS task role), instance profiles for EC2, cross-account roles, web identity/SAML roles
  • Service-linked roles are predefined by services
  • Passing a role to a service needs iam:PassRole; limit it by role ARN and iam:PassedToService

Best practices: no root usage (MFA on root), least privilege, groups for users, roles for apps, rotate and delete unused keys (credential report, access advisor shows last used), use Access Analyzer (external access findings and policy generation from CloudTrail), use conditions and tags for attribute-based access control (ABAC).

Good to know: IAM is global; IAM users can have max 2 access keys; MFA types: virtual app, FIDO security key, hardware token; password policy; aws sts decode-authorization-message to read encoded AccessDenied reasons; IAM policy simulator tests policies; the Shared Responsibility Model: AWS manages the cloud infrastructure, you manage IAM users, policies, MFA and key rotation.

Details

EC2 fundamentals

Purchasing options
  • On-Demand (no commitment), Reserved (1 or 3 years, big discount), Savings Plans (commitment in dollars per hour)
  • Spot (up to 90% off, can be interrupted with a 2 minute warning, good for stateless and batch)
  • Dedicated Host (physical server, licensing), Dedicated Instance, Capacity Reservation
Security groups
  • Only allow rules, stateful, evaluated as a whole. Default: all inbound blocked, all outbound allowed
  • Can reference other security groups. Ports: 22 SSH, 80 HTTP, 443 HTTPS, 3389 RDP
  • SSH times out = security group problem. "Connection refused" = application problem
Other
  • User Data runs once at first boot as root (bootstrap scripts). Runs again only if configured so
  • Instance Connect: browser-based SSH with temporary keys
  • Attach an IAM role through an instance profile. Metadata at 169.254.169.254
  • Instance families: T/M general, C compute, R/X memory, I/D storage, P/G accelerated
  • System status check = AWS hardware problem (stop/start moves the host). Instance status check = your OS/software problem (reboot, fix)
  • Public IP changes on stop/start, Elastic IP stays

EC2: networking, placement, metadata, AMI

Networking
  • ENI: virtual network card with private IP(s), optional public/Elastic IP, security groups, MAC address; can be moved between instances in the same AZ (failover trick)
  • Public IPv4 changes on stop/start; Elastic IP is static and remains yours (charged if unused or extra); private IP stays
  • Security groups: up to 5 per ENI by default, allow rules only, stateful; can reference other SGs; NACLs sit at the subnet level
  • ENA and Elastic Fabric Adapter (EFA) for high-performance networking
Placement groups
  • Cluster: same rack/AZ, lowest latency and highest throughput (HPC), risk: single point of failure
  • Spread: each instance on different hardware, max 7 per AZ per group, for small critical sets
  • Partition: instances in logical partitions on separate racks (Hadoop, Cassandra, Kafka), up to 7 partitions per AZ
Metadata and user data
  • Instance metadata: http://169.254.169.254/latest/meta-data/ (instance ID, public IP, IAM role credentials under iam/security-credentials/rolename); user data at /latest/user-data. Not encrypted and local only; IMDSv2 uses a session token (PUT then GET) and is more secure against SSRF
  • User data runs as root at first boot by default; size limit 16 KB

Instance types: naming (m5.large: family m, generation 5, size large). General purpose (M, T burstable with CPU credits), compute optimized (C), memory optimized (R, X, z), storage optimized (I, D, H), accelerated computing (P, G, Inf, Trn). Nitro system for performance.

Hibernate: saves RAM to an encrypted EBS root volume, fast resume; needs supported instance types and encrypted root volume.

Purchasing: On-Demand, Reserved (Standard, Convertible, 1/3 years), Savings Plans (Compute, EC2 Instance), Spot (2-minute interruption notice, Spot Fleet/Capacity-optimized), Dedicated Hosts (BYOL, compliance), Dedicated Instances, Capacity Reservations (no discount, guarantee capacity in an AZ).

AMI: region-scoped template (root volume snapshot + permissions + block device mapping); copy to other regions; share with accounts; encrypted AMIs need key sharing; pre-baked AMIs speed up scaling compared with long user data scripts. EC2 Image Builder automates AMI pipelines.

Access: SSH with key pair (22), EC2 Instance Connect (browser or CLI, temporary key), Session Manager (no open ports, IAM and audit, needs SSM agent and role). Serial console for boot problems.

EC2 and IAM: always use roles (instance profile). Tags and Systems Manager Run Command / Patch Manager help manage fleets.

Details
EBS
  • Network drive, bound to one AZ, normally attached to one instance (io1/io2 Multi-Attach: same AZ only)
  • Snapshots are stored in S3, can be copied across AZ and region (this is how you move a volume). Snapshot Recycle Bin protects from accidental deletion
  • Types: gp2/gp3 (general SSD, gp3 baseline 3,000 IOPS), io1/io2 (provisioned IOPS, databases), st1 and sc1 (HDD, cannot be boot volumes)
  • Root volume is deleted on termination by default, extra volumes are kept
  • Encryption uses KMS, transparent. Snapshots of encrypted volumes are encrypted

AMI: region specific, can be copied to another region, launch from custom AMI for faster boot.

Instance Store: physical disk on the host, very high performance, ephemeral (lost on stop/terminate or host failure). Good for cache and temporary data.

EFS
  • Managed NFS, shared by many instances across AZs, Linux only, pay per use, scales automatically
  • Performance modes: General Purpose, Max I/O. Throughput modes: Bursting, Provisioned, Elastic
  • Storage classes: Standard, IA, with lifecycle policies. Can be mounted by Lambda and ECS tasks
  • EBS vs EFS: EBS = one instance, one AZ, block storage. EFS = many instances, multi-AZ, file storage

Details

Load balancers and Auto Scaling

Load balancers
  • ALB: Layer 7 (HTTP, HTTPS, gRPC, WebSocket). Routes by path, host, header, query string. Targets: instances, IPs, Lambda. Client IP in X-Forwarded-For
  • NLB: Layer 4 (TCP, UDP, TLS), ultra-low latency, millions of requests, static IP / Elastic IP per AZ
  • GWLB: Layer 3, sends traffic to virtual appliances (firewalls), GENEVE protocol port 6081
  • Sticky sessions: ALB cookie (AWSALB) with duration 1 second to 7 days
  • Cross-zone: ALB on by default and free. NLB and GWLB off by default and cost inter-AZ traffic
  • SSL: certificates from ACM, SNI lets ALB and NLB serve many certificates (CLB only one)
  • Connection draining (CLB) / deregistration delay (ALB/NLB): default 300 seconds (1 to 3600), lets in-flight requests finish
Auto Scaling Group
  • Min, desired, max. Uses a launch template. Health checks: EC2 or ELB
  • Policies: target tracking (keep average CPU at 50%), step/simple (CloudWatch alarm), scheduled, predictive
  • Cooldown (default 300 s) prevents flapping. Lifecycle hooks pause launch or terminate
  • Instance Refresh: rolling replacement with minimum healthy percentage
  • Use custom metrics (for example SQS queue length per instance) to scale workers

ELB and Auto Scaling in depth

ALB details
  • Listeners (HTTP 80, HTTPS 443) with rules: conditions (path, host, header, query string, source IP, HTTP method) and actions (forward, redirect, fixed response, authenticate-oidc/cognito). Target groups: instance, IP (includes on-prem via VPN), Lambda. Weighted target groups for blue/green and canary
  • Health checks per target group (path, port, interval, healthy/unhealthy thresholds, success codes). Unhealthy targets receive no traffic; ASG with ELB health check type replaces them
  • Preserves client IP in the X-Forwarded-For header (also X-Forwarded-Port and -Proto). Supports HTTP/2, WebSockets, gRPC, TLS termination with ACM, SNI for many certificates, security policies
  • Sticky sessions with ALB-generated cookie (AWSALB), duration-based or application-based cookie; load balancing algorithm round robin or least outstanding requests
  • Idle timeout default 60 s. Access logs to S3. Cross-zone enabled by default. Integrates with WAF

NLB: TCP/UDP/TLS, one static IP (or Elastic IP) per AZ, preserves source IP, millions of requests per second, ultra-low latency, health checks TCP/HTTP, PrivateLink endpoint services, cross-zone off by default (extra charges if on)

GWLB: transparent network gateway plus load balancer for third-party virtual appliances (firewalls, IDS) using GENEVE port 6081

CLB: legacy; one certificate per load balancer; avoid for new work.

Connection draining / deregistration delay: 0-3,600 s, default 300 s.

Auto Scaling Group
  • Launch template (AMI, instance type, key, SG, user data, role; versions; mix of On-Demand and Spot with mixed instances policy). Min, desired, max capacity; multiple AZs for resilience
  • Scaling policies: target tracking (e.g. ASGAverageCPUUtilization 50%, ALBRequestCountPerTarget), step scaling (alarm thresholds with steps), simple scaling (one adjustment + cooldown), scheduled actions, predictive scaling. Custom CloudWatch metrics such as SQS backlog per instance
  • Cooldown (default 300 s) prevents rapid repeated actions; warm-up time for new instances; health check grace period (default 300 s) before health checks start
  • Health: EC2 status checks (default) and ELB health checks (enable for load balanced fleets). Unhealthy instances are terminated and replaced
  • Lifecycle hooks: pause an instance in Pending:Wait or Terminating:Wait to run scripts (install software, drain logs, deregister); notify via EventBridge/SNS/SQS; heartbeat timeout
  • Termination policy: default balances AZs, then oldest launch template/configuration, then closest to next billing hour; scale-in protection per instance
  • Instance Refresh: rolling replacement after changing launch template, with minimum healthy percentage and warm-up; warm pools keep pre-initialized stopped/hibernated instances for faster scale-out
  • Scheduled scaling for known peaks; Spot with capacity-optimized strategy; ASG sends notifications and integrates with CodeDeploy (new instances get the latest revision)

High availability: spread over at least 2 AZs, ELB in front, stateless app tier (sessions in ElastiCache/DynamoDB), data in RDS Multi-AZ/Aurora, static assets in S3 + CloudFront.

Details

RDS, Aurora, ElastiCache

RDS
  • Managed relational DB (MySQL, PostgreSQL, MariaDB, Oracle, SQL Server). No SSH access
  • Multi-AZ = synchronous standby for high availability and automatic failover (DNS name stays). NOT for scaling reads
  • Read replicas = asynchronous, up to 15, can be cross-region, can be promoted. For scaling reads
  • Automated backups: daily plus transaction logs, retention 1-35 days, point-in-time restore creates a NEW database
  • Encryption at rest must be chosen at creation (to encrypt later: snapshot, copy encrypted, restore). IAM database authentication for MySQL and PostgreSQL (15 minute tokens)
  • RDS Proxy: pools and shares connections, protects DB from Lambda connection storms, faster failover (up to 66%), IAM auth, credentials in Secrets Manager, only reachable inside VPC
Aurora
  • 6 copies of data across 3 AZs, storage grows 10 GB to 128 TB, up to 15 replicas, failover typically under 30 s
  • Writer endpoint and reader endpoint (load balances replicas). Serverless v2, Global Database, Backtrack (MySQL)
ElastiCache
  • Redis: Multi-AZ, replication, persistence, backup, rich data types (sorted sets), AUTH. Memcached: sharding, multi-threaded, no persistence or replication
  • Lazy loading (cache-aside): read from cache, on miss read DB and fill cache. Data can be stale. Write-through: update cache on each write. Always set a TTL
  • MemoryDB: durable Redis-compatible primary database

RDS, Aurora, ElastiCache details

RDS operations
  • Engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, plus Aurora; Custom for Oracle/SQL Server. You cannot SSH into the host; you manage parameter groups and option groups
  • Storage: gp2/gp3, io1/io2; storage autoscaling up to a maximum you set; scale compute by changing instance class (brief downtime unless Multi-AZ)
  • Backups: automated (daily snapshot + transaction logs, 1-35 days, 5-minute point-in-time restore granularity, restore to a NEW instance) and manual snapshots (kept until deleted, can be shared or copied across regions/accounts)
  • Maintenance windows, minor version upgrades; Multi-AZ failover reboots with DNS switch (60-120 s), standby is not readable (except Multi-AZ DB cluster with two readable standbys)
  • Read replicas: up to 15 (5 for some engines), async, same or different region/AZ, can be promoted, can themselves be Multi-AZ; you need to point the application at replica endpoints; data transfer between regions is charged
  • Security: VPC with private subnets, security groups, encryption at rest (KMS, chosen at creation; to encrypt an existing DB: snapshot, copy with encryption, restore), TLS in transit, IAM database authentication (token valid 15 minutes, MySQL and PostgreSQL), Secrets Manager rotation, CloudTrail
  • RDS Event notifications via SNS/EventBridge; Enhanced Monitoring (OS metrics), Performance Insights (query load)
  • RDS Proxy: connection pooling and multiplexing, fewer connections and CPU load, up to 66% faster failover, IAM authentication and secrets in Secrets Manager, supports Lambda well, reachable only in the VPC, supports MySQL/PostgreSQL/MariaDB/SQL Server
Aurora
  • Compute and storage are separated; storage in 10 GB chunks, 6 copies across 3 AZs, self-healing, up to 128 TB; tolerates loss of 2 copies for writes and 3 for reads
  • One writer + up to 15 readers (Aurora Replicas, low replica lag); failover promotes a replica, typically under 30 seconds; endpoints: cluster (writer), reader (load-balanced), custom, instance
  • Aurora Serverless v2 scales capacity automatically; Global Database (replication across regions with about 1 second lag, fast regional failover); Backtrack (rewind MySQL-compatible DB without restore); cloning (fast copy-on-write); Data API (HTTP access); Parallel Query; machine learning integration
  • Compatible with MySQL and PostgreSQL
ElastiCache
  • Redis (also Valkey): in-memory data structures (strings, hashes, lists, sets, sorted sets), replication, Multi-AZ with automatic failover, backup/snapshot, persistence, cluster mode (sharding), pub/sub, Lua, encryption at rest and in transit, AUTH tokens and IAM authentication
  • Memcached: simple key-value, multi-node sharding, multi-threaded, no persistence, no replication, no backup
  • Strategies: lazy loading (cache-aside; cache only what is requested; stale data possible, cache miss penalty), write-through (always fresh, wasted cache for unread data, write penalty), TTLs to limit staleness, combine lazy loading + write-through. Evictions happen when memory is full
  • Session store, leaderboard (sorted sets), caching DB results, rate limiting. In a VPC; apps connect through the cluster endpoint
  • MemoryDB for Redis: Redis-compatible, durable (multi-AZ transaction log) primary database, microsecond reads, single-digit-ms writes

VPC and Route 53 in depth

VPC design
  • VPC CIDR (/16 to /28, for example 10.0.0.0/16); subnets are in ONE AZ; AWS reserves 5 IP addresses per subnet (first four and last). Default VPC has public subnets in each AZ
  • Route tables decide where traffic goes: 0.0.0.0/0 to an Internet Gateway makes a subnet public; to a NAT gateway for private subnets; local route for VPC traffic
  • Internet Gateway (horizontally scaled, one per VPC); NAT Gateway (managed, per AZ, in a public subnet with an Elastic IP; create one per AZ for HA; NAT instances are legacy); Egress-only IGW for IPv6
  • Security group (instance/ENI level, allow only, stateful) vs NACL (subnet level, allow and deny, stateless, numbered rules evaluated in order, default allows all, remember ephemeral ports for returning traffic)
  • VPC Flow Logs (VPC, subnet or ENI level to CloudWatch Logs, S3 or Firehose; metadata only, REJECT/ACCEPT)
  • DNS settings: enableDnsSupport and enableDnsHostnames; private hosted zones for internal names
Connectivity
  • Peering: 1:1, private IPs, cross-account and cross-region, no overlapping CIDRs, NOT transitive, update both route tables, allow in security groups
  • Transit Gateway: hub-and-spoke connecting many VPCs and on-prem; Direct Connect (private dedicated connection, consistent latency) and Site-to-Site VPN (IPsec over internet, quick); Client VPN for remote users
  • VPC endpoints: gateway endpoints for S3 and DynamoDB (route table, free); interface endpoints (PrivateLink, ENI with private IP, DNS, security groups, charged per hour/GB) for most services and your own services; endpoint policies restrict what can be accessed
  • Lambda in VPC: attach to private subnets, needs NAT or endpoints for internet and AWS APIs; security groups control access to databases
  • Three-tier architecture: public subnets (ALB, NAT), private app subnets, private DB subnets; security groups chained by reference (ALB SG to app SG to DB SG)

S3: encryption and access control in depth

Encryption at rest
  • SSE-S3: keys fully managed by S3 (AES-256). Header x-amz-server-side-encryption: AES256. All new objects are encrypted with SSE-S3 by default
  • SSE-KMS: keys in KMS, header x-amz-server-side-encryption: aws:kms (optionally with key ID). Gives key policy control and CloudTrail audit. Each request calls KMS (GenerateDataKey/Decrypt), so very busy buckets can hit KMS quotas: use S3 Bucket Keys. Caller needs both S3 and KMS permissions
  • DSSE-KMS: two layers of encryption
  • SSE-C: you supply the key on every request, HTTPS mandatory, S3 does not store the key; you must send the same key again to read
  • Client-side encryption: you encrypt before upload (for example with the AWS Encryption SDK / envelope encryption)
  • Default encryption can be set per bucket; a bucket policy can DENY uploads that lack the right encryption header

Encryption in transit: HTTPS. Enforce with a bucket policy: Deny when aws:SecureTransport is false.

Access control
  • IAM policies (who in your account), bucket policies (resource-based, cross-account, conditions on IP, VPC endpoint aws:SourceVpce, MFA, encryption headers), ACLs (legacy, disabled by default with Bucket Owner Enforced)
  • Access allowed when an IAM policy OR bucket policy allows it (same account) and there is no explicit Deny. Cross-account needs both sides to allow
  • Block Public Access: overrides policies; keep on unless hosting a public website
  • Access Points: one policy and network origin per application on a shared bucket; Multi-Region Access Points for global routing
  • Pre-signed URLs: time-limited GET/PUT with the creator's permissions (SDK default expiry 1 h; max 7 days with IAM user keys; shorter with temporary credentials)
  • CORS: JSON config on the bucket that serves the cross-origin request (AllowedOrigins, AllowedMethods, headers)
  • Object Lock (WORM): governance or compliance mode, legal hold; MFA Delete: root only, needs versioning
  • Access logs (server access logging to another bucket), CloudTrail data events for object-level API audit, S3 Inventory, Macie for sensitive data discovery
  • Object Lambda: Lambda transforms data on GET (redact, resize, convert) without copies

Typical bucket policy conditions: s3:x-amz-server-side-encryption, aws:SecureTransport, aws:SourceVpce, s3:prefix, aws:PrincipalOrgID.

S3: classes, versioning, replication, events, performance

Storage classes
  • Standard: frequent access, ms latency. Intelligent-Tiering: automatic tiering, no retrieval fee, small monitoring fee
  • Standard-IA and One Zone-IA: infrequent access, retrieval fee, 30-day and 128 KB minimums; One Zone-IA stores in a single AZ (lower resilience, cheaper)
  • Glacier Instant Retrieval (ms access, 90-day min), Glacier Flexible Retrieval (expedited 1-5 min, standard 3-5 h, bulk 5-12 h, 90-day min), Glacier Deep Archive (standard 12 h, bulk 48 h, 180-day min)
  • Lifecycle rules: transitions (Standard to IA after 30 days, to Glacier after 90 days...) and expiration, for current/previous versions, incomplete multipart uploads
Versioning
  • Enabled per bucket, cannot be disabled (only suspended). Each object gets a version ID. DELETE without version ID adds a delete marker; delete of a version ID is permanent
  • Required for replication. Protects against accidental overwrite/delete
Replication
  • CRR (cross-region) and SRR (same-region); versioning on both buckets, IAM role, asynchronous, only NEW objects after enabling (use S3 Batch Replication for existing), no chaining (A to B to C does not cascade), delete markers optionally replicated
  • Use cases: compliance, lower latency, log aggregation, prod/test copies; Replication Time Control gives a 15-minute SLA

Event notifications: ObjectCreated, ObjectRemoved, ObjectRestore, Replication... to Lambda, SNS, SQS or EventBridge (EventBridge gives filtering, many targets, archive and replay). The destination needs a resource policy (or Lambda permission) allowing S3. Usually delivered within seconds, at-least-once.

Performance
  • Per prefix: 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second; spread data over prefixes for more
  • Multipart upload: recommended above 100 MB, required above 5 GB, parts 5 MB to 5 GB, up to 10,000 parts, parallel and retryable; clean up incomplete uploads with lifecycle
  • Transfer Acceleration (edge locations), byte-range fetches (parallel download or partial read), S3 Select / Glacier Select style filtering to fetch part of an object
  • Object tags (up to 10) and metadata (user-defined, 2 KB) cannot be searched directly; keep an index in DynamoDB or use Inventory/Athena
  • Static website hosting: index and error documents, public read needed (or CloudFront with OAC); website endpoint is HTTP only
  • Requester Pays: requester pays for requests and data transfer; S3 Inventory: daily/weekly object listing; Storage Lens and Analytics for usage insights

CloudFront in depth

Overview

Distribution parts: origins (S3 bucket, S3 website endpoint, ALB/EC2/custom HTTP, API Gateway, MediaPackage), cache behaviors (path pattern, origin, viewer protocol policy, allowed methods, cache policy, origin request policy, response headers policy, function associations), default behavior (*), alternate domain names with ACM certificate (us-east-1), price class, WAF web ACL, geo restriction, logging

Caching
  • Cache key = what identifies an object: path + chosen headers, cookies, query strings. Fewer items in the key = better hit ratio. Origin request policy forwards extra values to the origin WITHOUT adding them to the cache key
  • TTL: min, default (24 hours), max (1 year); origin can control with Cache-Control: max-age, s-maxage and Expires
  • Invalidation: CreateInvalidation with paths or wildcards (first 1,000 paths a month are free); versioned names (app.v3.js) avoid invalidation. Regional edge caches add a middle layer
  • Compression (gzip/brotli), HTTP/2 and HTTP/3, HTTPS to viewers and to origins, SNI
Origin security
  • S3: use Origin Access Control (OAC) (replaces OAI) and a bucket policy that only allows the distribution; keep the bucket private
  • ALB/EC2 origin: must be publicly reachable; restrict by allowing only CloudFront (managed prefix list or a secret custom header)
  • Origin groups: primary/secondary origins for failover on status codes
Restricting viewers
  • Signed URL (one object, any client type) vs signed cookies (many objects, keep URLs unchanged); created with a key pair from a key group (trusted key groups replace trusted signers/root keys); policy sets expiry, IP and resource; a canned policy is simpler
  • Geo restriction (allow list or block list by country); field-level encryption (encrypt specific form fields with a public key so only the app backend can decrypt); WAF; AWS Shield Standard protects automatically; HTTPS enforcement (redirect HTTP to HTTPS)
  • Do not mix up: S3 pre-signed URLs go straight to S3; CloudFront signed URLs go to CloudFront
Edge compute
  • CloudFront Functions: JavaScript, viewer request/response only, sub-millisecond, max 10 KB, 2 MB memory, no network/file access; use for URL rewrites, header manipulation, cache key normalization, simple auth
  • Lambda@Edge: Node.js/Python, viewer and origin request/response, up to 5 s (viewer) or 30 s (origin), can call other AWS services, deploy from us-east-1; use for heavier logic, A/B tests, SEO, dynamic origin selection

Logging and metrics: standard access logs to S3, real-time logs to Kinesis Data Streams, CloudWatch metrics (requests, error rates, cache hit rate), reports. Typical errors: 403 (OAC/policy, signed URL, geo), 502/503/504 (origin issues), stale content (TTL/invalidation).

Lambda: invocation types, event sources, errors

Three ways Lambda gets invoked
  1. Synchronous (RequestResponse): the caller waits for the result. Used by API Gateway, ALB, Cognito, CloudFront (Lambda@Edge), SDK/CLI with default type. Errors go back to the caller, the caller retries. Throttling returns 429.
  2. Asynchronous (Event): Lambda queues the event and returns 202 immediately. Used by S3, SNS, EventBridge, CodeCommit, IoT. Lambda retries failures 2 more times (waits 1 min, then 2 min). Max event age 6 hours (configurable). After the final failure the event goes to a DLQ (SQS or SNS) or an on-failure destination.
  3. Event source mapping: Lambda POLLS the source and invokes your function with batches. Sources: SQS (standard and FIFO), Kinesis Data Streams, DynamoDB Streams, MSK/Kafka. The function needs read permissions on the source in its execution role.

Destinations (async and stream failures): OnSuccess and OnFailure can go to SQS, SNS, another Lambda or EventBridge. Destinations carry more detail than a DLQ (response, error, request context). AWS recommends destinations over DLQ for new designs, DLQ still works.

Stream sources (Kinesis, DynamoDB Streams)
  • Records of a shard are processed in order, so one failing batch BLOCKS the shard until it succeeds or the records expire
  • Tools: BisectBatchOnFunctionError (split the batch to isolate the bad record), MaximumRetryAttempts, MaximumRecordAgeInSeconds, on-failure destination, ParallelizationFactor (1-10 batches per shard in parallel, order kept per partition key)
  • Metric IteratorAge shows how far behind the function is
SQS source
  • Lambda long-polls the queue and scales the number of pollers with queue depth. Batch size up to 10 (up to 10,000 for standard queues with a batching window)
  • Set the queue visibility timeout to at least 6x the function timeout. A failed batch returns after the visibility timeout. Put the DLQ on the QUEUE (not on the function)
  • ReportBatchItemFailures (partial batch response): return only the failed message IDs so successful ones are deleted
  • Limit load on a downstream system with maximum concurrency on the mapping or function reserved concurrency
  • FIFO queues: processing order per message group, concurrency limited by number of message groups

Idempotency: async retries and at-least-once sources mean the same event can arrive twice, so make handlers idempotent (conditional writes, idempotency keys, Powertools idempotency).

Event and context objects: event carries the trigger payload; context has request ID, function name/version, remaining time (getRemainingTimeInMillis), log group/stream.

Lambda: performance, concurrency, deployment, limits

Cold start and init
  • Cold start = new execution environment: download code, start runtime, run init code (outside the handler). Warm start reuses the environment
  • Reduce: smaller package, lazy-load libraries, avoid heavy init, SnapStart (Java, plus Python/.NET), provisioned concurrency
  • Create SDK clients and DB connections OUTSIDE the handler; keep temp files in /tmp (persists in a warm environment, not guaranteed)

Memory and CPU: 128 MB to 10,240 MB. CPU and network scale with memory (about 1 vCPU at 1,769 MB, up to 6 vCPUs). Often more memory = shorter duration = similar or lower cost. Use the Lambda Power Tuning tool to find the best value.

Concurrency
  • Account default 1,000 concurrent executions per region (soft limit). Each in-flight request uses one environment
  • Reserved concurrency: guarantees AND caps a function (protects downstream systems, and keeps other functions from starving). Setting it to 0 effectively disables the function
  • Provisioned concurrency: pre-initialized environments, no cold starts, you pay for it. Can be scheduled with Application Auto Scaling. Applies to a version or alias, not $LATEST
  • Throttled sync invocations return 429 (TooManyRequestsException); async ones are retried by Lambda for up to 6 hours

Versions and aliases: $LATEST is mutable; publishing makes an immutable numbered version. Aliases (PROD, DEV) point to versions and can split traffic by weight. Event sources should point to an alias. CodeDeploy can shift alias traffic (canary, linear) with alarms and rollback.

Layers: up to 5 per function, shared libraries/runtimes, counted in the 250 MB unzipped limit. Layer versions are immutable; functions pin a version.

Packaging: zip (50 MB direct upload, 250 MB unzipped including layers) or container image up to 10 GB from ECR (image must implement the runtime interface, base images provided). Large deps: layers, container images, or S3 upload.

Networking: default = no VPC, internet access. In a VPC the function gets ENIs (Hyperplane), reaches private resources, but needs NAT or VPC endpoints for internet/AWS APIs. Use RDS Proxy for databases.

Storage: /tmp 512 MB to 10 GB; EFS mount for shared persistent storage (function must be in the VPC).

Monitoring: CloudWatch metrics Invocations, Errors, Throttles, Duration, ConcurrentExecutions, IteratorAge, DeadLetterErrors, AsyncEventAge. Logs in /aws/lambda/name. X-Ray: enable active tracing. Insights and EMF for custom metrics.

Lambda@Edge vs CloudFront Functions: edge functions run on CloudFront events. Lambda@Edge (Node/Python, 4 event types, up to seconds) for heavy logic; CloudFront Functions (JS, viewer events, sub-ms, cheapest) for simple header/URL/redirect logic.

Env vars: 4 KB total, encrypted at rest by default, can use a customer KMS key and encryption helpers for extra protection in transit.

DynamoDB

Overview

Basics: NoSQL, item max 400 KB. Primary key = partition key, or partition + sort key. Good partition key = high cardinality, even access (avoid hot partitions)

Capacity: provisioned (with auto scaling) or on-demand

  • 1 RCU = one strongly consistent read per second up to 4 KB, or two eventually consistent reads. Transactional read = 2 RCU
  • 1 WCU = one write per second up to 1 KB. Transactional write = 2 WCU. Round UP to the 4 KB / 1 KB multiple
  • ProvisionedThroughputExceededException: use backoff, fix hot key, increase capacity or on-demand
Operations
  • GetItem, PutItem, UpdateItem (atomic counters), DeleteItem, Query (needs partition key, efficient), Scan (reads everything, expensive, filters apply after reading)
  • BatchGetItem 100 items/16 MB, BatchWriteItem 25 items/16 MB, transactions up to 100 items/4 MB
  • Pagination: LastEvaluatedKey becomes ExclusiveStartKey. Results max 1 MB per call. ProjectionExpression picks attributes
  • ConditionExpression: conditional writes, optimistic locking with version attribute. Failure = ConditionalCheckFailedException
Indexes
  • LSI: same partition key, different sort key, only at table creation, max 5, supports strong consistency
  • GSI: any keys, add anytime, own capacity (throttled GSI throttles the table writes), eventually consistent only

DynamoDB: capacity math, partitions and design

Capacity units (memorize and practice)
  • 1 RCU = 1 strongly consistent read/s of up to 4 KB = 2 eventually consistent reads/s of up to 4 KB
  • 1 WCU = 1 write/s of up to 1 KB
  • Transactional operations cost double (2 RCU per 4 KB read, 2 WCU per 1 KB write)
  • Item sizes round UP to the unit (4 KB for reads, 1 KB for writes)
Examples
  • 10 strongly consistent reads/s of 6 KB items: 6 KB rounds to 8 KB = 2 RCU each, total 20 RCU. Eventually consistent: 10 RCU
  • 100 eventually consistent reads/s of 8 KB: 2 units each, divide by 2 = 1 RCU each = 100 RCU
  • 5 writes/s of 2.5 KB: rounds to 3 WCU each = 15 WCU
  • 10 transactional writes/s of 3 KB: 3 x 2 = 6 WCU each = 60 WCU
Capacity modes
  • Provisioned: set RCU/WCU, optional auto scaling (target utilization), reserved capacity discount; burst capacity is a small safety net
  • On-demand: pay per request, no planning, handles spikes; good for unpredictable or new workloads (roughly 2.5x the cost per unit if traffic is steady)
  • Throttling: ProvisionedThroughputExceededException. The SDK retries with backoff. Solutions: on-demand, more capacity, better partition key, caching with DAX
Partitions
  • Data is spread by hash of the partition key; each partition serves a limited throughput (about 3,000 RCU and 1,000 WCU), and capacity is divided between partitions
  • A hot key (many requests to one key value) throttles even if the table total looks fine. Fix: high-cardinality keys, add a random or calculated suffix (write sharding), cache hot reads
  • Design for the access patterns first. Query by key is cheap; Scan is expensive. Avoid sequential keys like timestamps as the only partition key
Keys and indexes (recap)
  • Simple key (partition) or composite key (partition + sort). Item collection = same partition key
  • LSI: same partition key, other sort key, defined at table creation, max 5, shares table capacity, supports strong consistency, 10 GB limit per partition key value
  • GSI: any key, create or delete anytime, own capacity, eventual consistency only, throttled GSI back-pressures table writes, default max 20

Item and API limits: item 400 KB (use S3 for big objects), Query/Scan page 1 MB, BatchGetItem 100 items / 16 MB, BatchWriteItem 25 items / 16 MB (not atomic, unprocessed items must be retried), transactions up to 100 items / 4 MB

DynamoDB: operations, expressions, features

Reading
  • GetItem (by full key), Query (partition key + optional sort key condition via KeyConditionExpression), Scan (whole table; use parallel scan with Segment/TotalSegments for speed, but it is still expensive)
  • FilterExpression filters AFTER the read: you still pay RCU for everything read. ProjectionExpression only limits returned attributes
  • ConsistentRead=true for strong consistency (not on GSIs). Default is eventually consistent. Limit caps items evaluated
  • Pagination: pass LastEvaluatedKey as ExclusiveStartKey until it is absent
Writing
  • PutItem (replaces whole item), UpdateItem (change attributes, creates item if missing; SET, REMOVE, ADD, DELETE), DeleteItem
  • Atomic counter: SET views = views + :inc. No read-modify-write needed
  • Conditional writes: ConditionExpression (for example attribute_not_exists(pk) for insert-if-absent). Failure raises ConditionalCheckFailedException
  • Optimistic locking: keep a version attribute, condition version = :expected, increment on success
  • Transactions: TransactWriteItems and TransactGetItems (all or nothing, 2x capacity cost)
  • PartiQL: SQL-like syntax over the same engine
Features
  • Streams: ordered change log per item, 24 h retention, view types KEYS_ONLY, NEW_IMAGE, OLD_IMAGE, NEW_AND_OLD_IMAGES; Lambda polls it; also feeds cross-region replication (Global Tables)
  • TTL: attribute with epoch seconds; background deletion free of write capacity, often within 48 hours; deletions appear in Streams
  • DAX: write-through in-memory cache cluster, microsecond reads, same API through the DAX client, item cache and query cache (5 min default TTL), eventually consistent reads only; not for strongly consistent or write-heavy workloads
  • Global Tables: multi-region active-active, last-writer-wins, needs Streams (new and old images)
  • Backups: on-demand, point-in-time recovery (35 days, per second), export to S3, import from S3
  • Security: IAM policies (fine-grained with dynamodb:LeadingKeys), encryption at rest always on (AWS owned, AWS managed or customer managed KMS key), VPC gateway endpoint, CloudTrail for control plane
  • CLI: --projection-expression, --filter-expression, --page-size, --max-items, --starting-token

Patterns: session store (TTL), large payload in S3 + pointer item, leaderboard with GSI, adjacency list, single-table design for related entities.

User Pools

Step Functions in depth

Overview

Amazon States Language (JSON): StartAt, States; each state has Type, Next or End: true

  • Task (do work: Lambda, ECS, Batch, DynamoDB, SQS, SNS, SDK integrations for 200+ services), Choice (branch on input), Wait (seconds or timestamp), Parallel (run branches concurrently), Map (iterate over an array; inline or distributed for massive scale), Pass (pass/transform data), Succeed, Fail
  • Integration patterns: Request Response (default), Run a Job .sync (wait until the job completes, for Batch, ECS, Glue...), Wait for Callback with Task Token .waitForTaskToken (human approval, external systems; call SendTaskSuccess / SendTaskFailure, use HeartbeatSeconds / TimeoutSeconds)
  • Activity tasks: workers poll GetActivityTask (legacy way to include external workers)

Data flow: the state input goes through InputPath (filter) then Parameters (build task input), the task result goes through ResultSelector, ResultPath (where to put the result in the original input; null discards it), and OutputPath. JSONPath is used (or JSONata in newer definitions). Payload limit 256 KB per state; store larger data in S3.

Error handling
  • Retry: ErrorEquals, IntervalSeconds (default 1), BackoffRate (default 2), MaxAttempts (default 3), JitterStrategy
  • Catch: ErrorEquals, Next, ResultPath (to keep the error info). Built-in errors: States.ALL, States.Timeout, States.TaskFailed, States.Permissions, States.HeartbeatTimeout, States.DataLimitExceeded
  • Retries are evaluated first, then catchers. Lambda service errors (Lambda.ServiceException, TooManyRequestsException) should be retried
  • TimeoutSeconds on tasks prevents hangs

SQS

SQS in depth

Overview

Basics: producers send, consumers poll. Standard queues: nearly unlimited throughput, at-least-once delivery, best-effort ordering. Message size 1 byte to 256 KB. Large payloads: SQS Extended Client Library with S3.

Key settings
  • Retention: 60 seconds to 14 days, default 4 days
  • Visibility timeout: 0 s to 12 h, default 30 s. While a message is being processed it is invisible; if not deleted before the timeout it becomes visible again. ChangeMessageVisibility extends the timeout for slow messages
  • Delay queue: 0 to 15 minutes on the queue; per-message DelaySeconds for standard queues
  • Long polling: ReceiveMessageWaitTimeSeconds or WaitTimeSeconds 1-20 s: fewer empty responses, lower cost, lower latency. Short polling returns immediately
  • MaxNumberOfMessages up to 10 per receive; batch send/delete up to 10 messages
  • Dead Letter Queue: RedrivePolicy with maxReceiveCount; DLQ must be the same type (standard or FIFO) and in the same account and region; set DLQ retention longer than the source; redrive back to the source after fixing the bug
  • Encryption at rest: SSE-SQS or SSE-KMS; in transit HTTPS. Access policy (resource-based) for cross-account senders and for SNS/S3/EventBridge to send messages
FIFO queues
  • Name ends with .fifo. Exactly-once processing within the 5-minute deduplication window; strict order per MessageGroupId (required). Different groups are processed in parallel, so many groups = more concurrency
  • Deduplication: MessageDeduplicationId or content-based deduplication (SHA-256 of body)
  • Throughput 300 messages/s (3,000 with batching), higher with high-throughput FIFO mode. Cannot convert a standard queue to FIFO
  • FIFO + Lambda: one batch per message group at a time
Patterns
  • Decouple tiers: web tier puts jobs in SQS, ASG of workers scales on ApproximateNumberOfMessagesVisible divided by instances (custom metric)
  • Fan-out: SNS topic to many SQS queues
  • Request-response and buffering for spikes; DLQ for poison messages; idempotent consumers because of duplicates
  • Operations: SendMessage, ReceiveMessage, DeleteMessage (must delete after success), PurgeQueue (deletes everything, takes up to 60 s), CloudWatch metrics ApproximateAgeOfOldestMessage, NumberOfMessagesSent
  • Consumers: EC2, ECS, Lambda (event source mapping, batch, partial failures), on-prem apps through SDK

SNS, Kinesis, Firehose in depth

SNS
  • Pub/sub: publishers send to a topic, every subscription gets a copy (fan-out). Subscribers: SQS, Lambda, HTTP(S), email, SMS, mobile push, Firehose. Up to 12.5 million subscriptions per topic, 100,000 topics
  • Publish with the SDK (Publish to a topic ARN) or through integrations (CloudWatch Alarms, S3 events, Budgets...). Direct publish for mobile push endpoints
  • Filter policies on subscriptions: attribute-based (or body-based) filtering, so subscribers only receive relevant messages
  • FIFO topics: ordering and dedup, subscribers must be SQS FIFO queues
  • Delivery retries with backoff; a subscription DLQ (SQS) catches messages that could not be delivered; message encryption with KMS; access policy for cross-account
  • Message size 256 KB; message attributes carry metadata
Kinesis Data Streams
  • Stream = shards. Per shard: write 1 MB/s or 1,000 records/s; read 2 MB/s (shared) and 5 reads/s. Record up to 1 MB. Retention 24 hours (default) up to 365 days; replay possible
  • Capacity modes: provisioned (you set shards, reshard by split/merge) and on-demand (auto scaling)
  • Ordering per partition key (same key, same shard). Bad keys create hot shards. PutRecord / PutRecords (batch, up to 500); Kinesis Producer Library batches, aggregates and retries; client throttling shows ProvisionedThroughputExceededException (retry with backoff, better key, more shards)
  • Consumers: Lambda, Kinesis Client Library (KCL; uses DynamoDB for checkpoints and shard leases, one worker per shard), SDK GetRecords, Firehose, Managed Flink
  • Shared throughput consumers split the 2 MB/s per shard; Enhanced Fan-Out gives each registered consumer its own 2 MB/s per shard with push (SubscribeToShard, HTTP/2), lower latency
  • Security: IAM, KMS server-side encryption, VPC endpoints
Amazon Data Firehose (Kinesis Data Firehose)
  • Fully managed delivery, near real time (buffer by size and time, as low as 0-60 s), no shards or consumers to manage, auto scaling
  • Sources: producers (SDK, agents), Kinesis Data Streams, CloudWatch Logs/Events, IoT. Destinations: S3, Redshift (via S3 COPY), OpenSearch, Splunk, HTTP endpoints, partner services
  • Optional Lambda transformation and format conversion (JSON to Parquet/ORC), compression, encryption; failed records go to an S3 backup bucket
  • Not for replay, no multiple consumers; use Streams when you need custom processing, ordering, replay

Managed Service for Apache Flink: real-time SQL/Java analytics on streams. MSK: managed Kafka (choose when you already use Kafka).

Choosing
  • SQS: decouple/buffer, one consumer group, delete after processing, no replay
  • SNS: fan-out/notifications, push, no persistence
  • Kinesis Streams: ordered streaming, multiple consumers, replay, real time analytics
  • Firehose: simply land streaming data into S3/Redshift/OpenSearch
  • EventBridge: event routing between AWS services and SaaS with content filtering and schedules

Elastic Beanstalk: deployments, config, operations

Deployment policies compared
  • All at once: all instances updated together. Fastest, downtime during the update, no extra cost, rollback = redeploy old version
  • Rolling: instances updated in batches (bucket size). No downtime but reduced capacity while a batch is updated, versions are mixed. No extra cost
  • Rolling with additional batch: starts a new batch first, so full capacity stays. Small extra cost, mixed versions
  • Immutable: new instances in a temporary ASG with the new version; if healthy, they join the main ASG and old ones go away. Zero downtime, full capacity, safest, quick rollback (terminate new ASG), double capacity temporarily
  • Traffic splitting: immutable-like with a canary percentage of traffic for an evaluation time, automatic rollback if unhealthy
  • Blue/Green: not a built-in policy. Clone to a new environment, test, then swap environment URLs (CNAME swap). Route 53 weighted records can shift gradually. Database should be outside the environment

CloudFormation

Overview

Template sections: Resources (only required one), Parameters, Mappings, Conditions, Outputs, Metadata, Transform

Intrinsic functions: Ref, Fn::GetAtt, Fn::FindInMap, Fn::ImportValue, Fn::Join, Fn::Sub, Fn::If, Fn::Base64

Rollbacks

  • Update fails: automatic rollback to the previous state. UPDATE_ROLLBACK_FAILED: fix the problem and run ContinueUpdateRollback

  • Custom resources: Lambda or SNS backed (ServiceToken), for things CloudFormation does not support
  • StackSets: deploy the same stack to many accounts and regions

  • Secrets: dynamic references {{resolve:ssm:...}} and {{resolve:secretsmanager:...}}

CloudFormation: syntax, functions, behavior

Template skeleton (YAML)

AWSTemplateFormatVersion, Description, Metadata, Parameters, Mappings, Conditions, Transform, Resources (required), Outputs

Parameters: types String, Number, List, CommaDelimitedList, AWS-specific (AWS::EC2::KeyPair::KeyName, AWS::EC2::VPC::Id), SSM parameter types (AWS::SSM::Parameter::Value<String>). Constraints: AllowedValues, AllowedPattern, Min/MaxLength, Min/MaxValue, Default, NoEcho (masks in console, NOT a secret store)

Pseudo parameters: AWS::Region, AWS::AccountId, AWS::StackName, AWS::StackId, AWS::Partition, AWS::NoValue

Functions
  • Ref (parameter value or resource ID/name), Fn::GetAtt (specific attribute such as Arn, DNSName), Fn::Sub (string substitution with ${}), Fn::Join, Fn::Select, Fn::Split, Fn::FindInMap, Fn::GetAZs, Fn::ImportValue, Fn::Base64 (for user data), Fn::If/Fn::Equals/Fn::And/Fn::Or/Fn::Not, Fn::Transform
  • Dynamic references: {{resolve:ssm:name}}, {{resolve:ssm-secure:name}}, {{resolve:secretsmanager:id:SecretString:field}}
Stack behavior
  • Resources are created in dependency order (Ref/GetAtt create implicit dependencies; DependsOn makes explicit ones); independent resources are created in parallel
  • Update behaviors per property: no interruption, some interruption, or replacement (new resource created first, then old deleted; physical ID changes)
  • Rollback: failed create rolls the whole stack back (state ROLLBACK_COMPLETE, can only delete; option to disable rollback to inspect). Failed update returns to the previous state (UPDATE_ROLLBACK_COMPLETE). UPDATE_ROLLBACK_FAILED: fix the cause (or skip resources) and ContinueUpdateRollback
  • Change sets preview changes. Drift detection compares real vs template. Stack policy blocks updates to chosen resources. Termination protection blocks stack deletion. DeletionPolicy (Delete, Retain, Snapshot) and UpdateReplacePolicy protect data
  • Service role: CloudFormation acts with that role instead of the caller (needs iam:PassRole for the caller)
  • Capabilities: IAM resources need CAPABILITY_IAM or CAPABILITY_NAMED_IAM (custom names); macros and nested transforms need CAPABILITY_AUTO_EXPAND

Reuse: nested stacks (AWS::CloudFormation::Stack), cross-stack references (Outputs + Export + ImportValue; exports cannot be deleted while imported), StackSets (many accounts/regions), modules, macros

Custom resources: Custom::Name with ServiceToken (Lambda ARN or SNS topic). CloudFormation sends Create/Update/Delete requests; the handler must reply to the pre-signed S3 URL (cfn-response) or the stack hangs until timeout

EC2 helper scripts: cfn-init (read AWS::CloudFormation::Init metadata: packages, files, services), cfn-signal (tell CloudFormation about success), cfn-hup (apply metadata updates), with CreationPolicy or WaitCondition

Limits: 500 resources per stack, 200 parameters, 200 outputs, template body 51,200 bytes inline or 1 MB from S3.

Strategies (concepts)
  • All at once: replace everything now. Fast, downtime, hard rollback
  • Rolling: replace in batches. Reduced capacity during update, mixed versions
  • Rolling with additional batch: add capacity first, then roll. No capacity loss
  • Immutable: new fleet beside the old, switch when healthy. Safe, costs more temporarily
  • Blue/Green: two full environments, switch traffic (DNS, ALB target groups, CNAME swap). Instant rollback, double cost during the switch
  • Canary: send a small percentage first, watch metrics, then the rest
  • Linear: increase percentage in equal steps at intervals
Service by service
  • Elastic Beanstalk: all at once, rolling, rolling with additional batch, immutable, traffic splitting (canary); blue/green by swapping environment URLs
  • CodeDeploy EC2/on-prem: in-place (AllAtOnce, HalfAtATime, OneAtATime, custom) or blue/green (new ASG, ELB traffic switch)
  • CodeDeploy Lambda: Canary (Canary10Percent5Minutes/10Minutes/15Minutes/30Minutes), Linear (Linear10PercentEvery1/2/3/10Minutes), AllAtOnce; shifts alias traffic; hooks BeforeAllowTraffic/AfterAllowTraffic; rollback on alarm
  • CodeDeploy ECS: blue/green with ALB, canary/linear/all-at-once traffic shifting between task sets
  • ECS service (without CodeDeploy): rolling update using minimumHealthyPercent and maximumPercent; deployment circuit breaker rollback
  • Lambda alone: alias with weighted routing between two versions
  • API Gateway: canary release on a stage (percentage to new deployment), stage variables per environment
  • Route 53: weighted routing for gradual shifts, failover for DR
  • ASG: instance refresh (rolling, min healthy percentage), launch templates versions
  • CloudFormation: updates in place or replacement; change sets; rolling update policies for ASG resources (UpdatePolicy: AutoScalingRollingUpdate, AutoScalingReplacingUpdate); CreationPolicy for signals
Developer best practices frequently tested
  • Stateless applications: sessions in ElastiCache/DynamoDB, files in S3/EFS
  • Decouple with queues and events (SQS, SNS, EventBridge); idempotent consumers; DLQs for poison messages
  • Retry with exponential backoff and jitter; set timeouts; circuit breakers
  • Cache close to the user (CloudFront) and close to the data (DAX, ElastiCache, API Gateway cache); choose TTLs
  • Least privilege IAM; roles instead of keys; secrets in Secrets Manager/Parameter Store; encrypt at rest and in transit
  • Infrastructure as code (CloudFormation/SAM/CDK) and CI/CD (CodePipeline); separate environments via parameters or accounts

KMS, Encryption SDK, SSM, Secrets Manager

KMS
  • Key types: AWS owned, AWS managed (aws/s3, rotated yearly automatically), customer managed (you control policy and rotation, small monthly fee), symmetric (AES-256, never leaves KMS) and asymmetric (RSA/ECC, public key downloadable)
  • Keys are regional. Copying encrypted snapshots to another region re-encrypts with a key from that region. Multi-Region keys have the same key ID in several regions
  • Key policy is required (default allows the account to use IAM policies). Grants give temporary permissions
  • Encrypt/Decrypt handle only up to 4 KB. For bigger data use envelope encryption: GenerateDataKey returns plaintext + encrypted data key, encrypt data locally, store encrypted data key with the data. AWS Encryption SDK does this (and data key caching)
  • Quotas per region (5,500 / 10,000 / 30,000 requests per second, shared). Throttling: backoff, data key caching, S3 Bucket Keys
  • CloudHSM: dedicated single-tenant HSM, you manage keys, FIPS 140-2 Level 3

SSM Parameter Store: hierarchy (/app/prod/db), String, StringList, SecureString (KMS). Standard: 4 KB, free. Advanced: 8 KB, parameter policies (expiration), more parameters. GetParameter --with-decryption, GetParametersByPath. Versions and change notifications via EventBridge

Secrets Manager: secrets with automatic rotation (Lambda), native RDS/Aurora/Redshift integration, multi-region replication, cross-account via resource policy, paid per secret

Parameter Store vs Secrets Manager: rotation and RDS integration = Secrets Manager, cheap config = Parameter Store

Other: CloudWatch Logs encryption with KMS on log group. CodeBuild: secrets via Parameter Store or Secrets Manager, never plaintext. Nitro Enclaves: isolated VM for very sensitive data processing. Lambda env vars: encryption helpers, KMS

KMS, SSM, Secrets Manager in depth

KMS keys
  • Types: symmetric (AES-256-GCM, most services) and asymmetric (RSA, ECC: encrypt/decrypt or sign/verify, public key exportable); HMAC keys. Origin: KMS generated, imported material, CloudHSM custom key store, external key store
  • Managed by: AWS owned keys (invisible, free), AWS managed keys (aws/s3, aws/ebs; rotate every year automatically; you cannot edit the policy), customer managed keys (you control policy; rotation is optional: automatic yearly rotation keeps the key ID; $1/month plus usage)
  • Key policy is the main control; the default policy lets the account root and therefore IAM policies manage access. Grants: temporary, programmatic delegation (used by EBS, RDS...). Key states: enabled, disabled, pending deletion (7 to 30 day waiting period)
  • Keys are regional; Multi-Region keys replicate key material with the same key ID across regions for global encryption or DynamoDB Global Tables
  • Aliases (alias/my-key) make rotation or replacement easy; kms:ViaService restricts use to a given service; encryption context is additional authenticated data (not secret) that must match when decrypting and shows in CloudTrail

APIs: Encrypt and Decrypt (data up to 4 KB), GenerateDataKey (plaintext + encrypted copy for envelope encryption), GenerateDataKeyWithoutPlaintext, ReEncrypt, CreateGrant, GenerateRandom

Envelope encryption flow: 1) call GenerateDataKey 2) encrypt data locally with the plaintext key, then discard it from memory 3) store ciphertext + encrypted data key 4) to decrypt: send encrypted data key to KMS Decrypt, get plaintext key, decrypt locally. The AWS Encryption SDK does all of this and supports data key caching to reduce KMS calls.

Quotas: request rates per region (5,500, 10,000 or 30,000 requests/s depending on the region and API, shared across all keys); ThrottlingException means back off, cache data keys, use S3 Bucket Keys, or request a quota increase.

Integrations: S3 (SSE-KMS, bucket keys), EBS (volume and snapshot encryption; encrypt an unencrypted volume by snapshot, copy encrypted, restore), RDS (at creation; replicas and snapshots inherit), DynamoDB, SQS, SNS, Lambda environment variables, CloudWatch Logs groups, CodeBuild and CodePipeline artifacts, Secrets Manager, SSM SecureString.

CloudHSM: dedicated HSM you control (FIPS 140-2 Level 3), single tenant, keys not accessible to AWS, you manage availability (cluster across AZs) and users; use for strict compliance or custom crypto (PKCS#11, JCE, CNG). KMS can use CloudHSM as a custom key store.

SSM Parameter Store
  • Types String, StringList, SecureString (KMS). Tiers: Standard (up to 10,000 parameters, 4 KB, free), Advanced (100,000 parameters, 8 KB, parameter policies like expiration and notification, charged)
  • Hierarchy such as /myapp/dev/db-url; GetParametersByPath with recursion for all values of an environment; versions and labels; change events to EventBridge; public AWS parameters (latest AMI IDs); CloudFormation parameter types and dynamic references
  • IAM controls access per path; --with-decryption needs kms:Decrypt
Secrets Manager
  • Stores secrets (up to 64 KB), automatic rotation by Lambda (ready templates for RDS, Aurora, Redshift, DocumentDB; custom for others), replication to other regions, resource policies for cross-account access, versions with staging labels (AWSCURRENT, AWSPREVIOUS), billed per secret per month plus API calls
  • Apps fetch the secret at runtime (cache it, caching libraries exist). Native RDS integration can manage the master password

Choose: configuration and cheap secrets without rotation = Parameter Store; rotation, RDS integration, multi-region replication = Secrets Manager.

Other security notes: CodeBuild must not use plaintext secrets; CloudWatch Logs encryption uses a KMS key on the log group; ACM certificates are free and renew automatically (public ones cannot be exported); Nitro Enclaves isolate sensitive computation inside an instance with no external network or persistent storage; GuardDuty detects threats, Inspector scans vulnerabilities, Macie finds sensitive S3 data, WAF filters HTTP requests, Shield protects against DDoS, Security Hub aggregates findings, Config tracks compliance.

CloudWatch, X-Ray, CloudTrail, EventBridge

Overview

CloudWatch Metrics: namespace + dimensions. EC2 basic 5 min, detailed 1 min. Custom metrics: PutMetricData, high resolution down to 1 s. Embedded Metric Format (EMF) puts metrics inside logs

Logs: log groups and streams, retention policy, metric filters, subscription filters (to Kinesis, Firehose, Lambda), export to S3 (CreateExportTask, not real time), Logs Insights (query), Live Tail. Unified CloudWatch agent sends memory and disk metrics and logs from EC2

Alarms: states OK, ALARM, INSUFFICIENT_DATA. Actions: SNS, EC2, Auto Scaling. Composite alarms combine alarms with AND/OR. Synthetics canaries: scripted checks of endpoints

EventBridge: event buses, rules with event patterns or schedules (cron/rate), targets (Lambda, SQS, SNS, Step Functions...), cross-account and schema registry

X-Ray (distributed tracing)

  • Segments and subsegments, service map. Annotations = indexed key-value (for filtering), metadata = not indexed
  • Needs SDK instrumentation plus X-Ray daemon (on Lambda active tracing does it). IAM permission xray:PutTraceSegments
  • Sampling rules: default 1 request per second plus 5% of additional requests. Env var AWS_XRAY_DAEMON_ADDRESS
  • Elastic Beanstalk: enable in console or .ebextensions. ECS: run daemon as a sidecar container

CloudTrail: records API calls (who, what, when). Management events on by default, data events (S3 objects, Lambda invokes) off by default. 90 days history, longer in S3. Insights detects unusual activity

Compare: CloudWatch = metrics/logs/alarms, X-Ray = request tracing and latency, CloudTrail = audit of API calls.

CloudWatch, X-Ray, CloudTrail in depth

CloudWatch metrics
  • Namespace (AWS/EC2) + metric name + dimensions (InstanceId). Default period 5 minutes for EC2 basic monitoring, 1 minute with detailed monitoring; custom metrics standard resolution 1 minute, high-resolution 1 second (StorageResolution=1)
  • Not available by default for EC2: memory, disk space and processes; use the CloudWatch agent. Lambda, API Gateway, SQS, DynamoDB publish their own metrics
  • PutMetricData publishes custom metrics (batch up to 1,000 values); Embedded Metric Format lets logs produce metrics without API calls
  • Retention: 1 s data 3 hours, 1 min 15 days, 5 min 63 days, 1 hour 455 days
  • Metric math, anomaly detection, dashboards (cross-region, cross-account)
Alarms
  • Evaluate a metric over periods: Period, EvaluationPeriods, DatapointsToAlarm, threshold, and TreatMissingData (missing, notBreaching, breaching, ignore)
  • States OK, ALARM, INSUFFICIENT_DATA. Actions: SNS, EC2 (stop, terminate, reboot, recover), Auto Scaling, Systems Manager OpsItems. Composite alarms combine alarms with AND/OR/NOT to reduce noise
  • Alarm on custom metrics (queue depth per instance) to scale; alarm on a metric filter derived from logs; alarms trigger CodeDeploy rollback
CloudWatch Logs
  • Log group (retention and encryption set here, default never expire) contains log streams. Agents, Lambda, ECS awslogs driver, API Gateway and many services send logs
  • Metric filters: pattern to count/measure matching lines, then alarm. Subscription filters stream logs in near real time to Kinesis Streams/Firehose/Lambda (and OpenSearch via those) and across accounts
  • Export to S3: CreateExportTask (can take up to 12 hours, not real time). Logs Insights: query language (fields, filter, stats, sort, limit, parse) across log groups. Live Tail: real-time view. Data protection policies mask sensitive data
  • Unified CloudWatch agent: metrics (memory, disk) and logs from EC2/on-premises via config file or Systems Manager Parameter Store; needs an IAM role (CloudWatchAgentServerPolicy)
  • CloudWatch Synthetics: canary scripts; RUM for real user monitoring; Container Insights; Lambda Insights; Contributor Insights

EventBridge: event buses (default, custom, partner, cross-account/region), rules (event pattern or schedule: rate(5 minutes), cron(0 6 * * ? *)), targets (Lambda, SQS, SNS, Step Functions, ECS tasks, API destinations...), archive and replay, schema registry, Pipes, Scheduler. AWS service events (EC2 state change, CodePipeline, GuardDuty, CloudTrail API calls) arrive here.

X-Ray
  • Trace = request path; segment = work done by one service; subsegment = downstream call. Service map and trace analytics. Annotations (indexed key-value for filter expressions) vs metadata (not searchable)
  • Instrument code with the X-Ray SDK or the OpenTelemetry-based AWS Distro (ADOT); the X-Ray daemon (UDP port 2000) relays segments to the service; Lambda and API Gateway integrate through active tracing; Elastic Beanstalk via setting; ECS with a daemon sidecar
  • IAM: xray:PutTraceSegments and xray:PutTelemetryRecords for the app, read access for viewing
  • Sampling: default one request per second and 5% of additional requests per host; custom sampling rules reduce cost. APIs: GetTraceSummaries, BatchGetTraces, GetServiceGraph
  • Why traces might be missing: no instrumentation, no permissions, daemon unreachable, sampling

CloudTrail: management events (default on, 90 days in Event history), data events (S3 objects, Lambda invokes, DynamoDB items; extra cost), Insights events (unusual activity). Create a trail for longer retention to S3 (+ CloudWatch Logs), multi-region and organization trails, log file integrity validation. Integrates with EventBridge for reacting to API calls (for example alert when someone deletes a table).

Rule of thumb: CloudWatch = performance and logs, X-Ray = request tracing, CloudTrail = who did what, AWS Config = resource configuration history and compliance.

Troubleshooting playbook (part 1): errors and symptoms

HTTP and API errors
  • API Gateway 400: bad request/validation; 403: auth failed, IAM/authorizer deny, WAF, resource policy, or missing route (Missing Authentication Token); 429: throttled (retry with backoff, usage plan, raise limits, cache); 502: invalid Lambda proxy response or backend crash; 503: backend unavailable; 504: integration took longer than 29 s
  • ALB 502: target closed connection or returned malformed response; 503: no healthy targets; 504: target did not respond in the idle timeout; 400: malformed request; 403: WAF or auth; check health checks, security groups (ALB to targets), ports and listener rules
  • CloudFront 403: OAC/bucket policy wrong, signed URL invalid, geo restriction; 502/504: origin unreachable or slow; stale content: TTL or invalidation
  • S3: 403 AccessDenied (policy, ACL, KMS permission, Block Public Access, VPC endpoint policy, wrong account), 404 NoSuchKey, 503 SlowDown (very high request rate to one prefix: spread and retry), 307 redirect for new buckets (DNS propagation)
  • DynamoDB: ProvisionedThroughputExceededException (hot partition, low capacity, throttled GSI), ConditionalCheckFailedException (expected under contention), ValidationException (item over 400 KB, wrong types, bad key), ResourceNotFoundException (wrong table or region)
Lambda
  • Timeout (Task timed out): raise timeout/memory, optimize, move heavy work to Step Functions/Fargate; check downstream latency
  • Out of memory (Runtime exited with error: signal: killed / Max Memory Used = memory size): increase memory
  • Throttles / 429: concurrency exhausted or reserved concurrency too low; use provisioned/reserved concurrency, SQS buffering
  • VPC function cannot reach internet/AWS APIs: NAT gateway or VPC endpoints; check security groups
  • AccessDenied calling other services: execution role missing permission; cannot be invoked: resource-based policy missing
  • Duplicate processing: async retries, at-least-once sources, visibility timeout too short; make functions idempotent
  • Stream consumer stuck / IteratorAge rising: poison record, slow function; bisect batch, max retries, on-failure destination, more parallelization, more shards
  • Cold start latency: provisioned concurrency, SnapStart, smaller package, move init out of handler
  • Unable to import module: wrong handler path/package, missing dependency or layer, wrong architecture or runtime
  • Logs missing: execution role lacks CloudWatch Logs permissions
Messaging
  • SQS messages reappearing: visibility timeout too short or message not deleted; poison messages go to DLQ via maxReceiveCount; messages disappear after retention (4 days default); FIFO ordering requires MessageGroupId; empty receives with short polling: use long polling
  • Kinesis ProvisionedThroughputExceeded on writes: hot shard (key), too many records; on reads: too many consumers on shared throughput, use Enhanced Fan-Out
  • SNS message not delivered: subscription not confirmed, filter policy mismatch, SQS queue policy does not allow SNS, endpoint down (check subscription DLQ)

Troubleshooting playbook (part 2): deployment, networking, security, tools

CloudFormation
  • CREATE_FAILED then ROLLBACK_COMPLETE: read the Events tab for the first failed resource; delete and recreate. UPDATE_ROLLBACK_FAILED: ContinueUpdateRollback (skip resources if needed). DELETE_FAILED: non-empty S3 bucket, resource in use, dependent export imported elsewhere
  • InsufficientCapabilitiesException: pass the IAM/AUTO_EXPAND capability. Custom resource hangs: handler never sent the response (timeout, no cfn-response). Drift: manual change outside the stack; run drift detection. Parameter or limit errors: service quotas
CI/CD
  • CodeBuild: check phase logs; Docker needs privilegedMode; AccessDenied for ECR/S3/Secrets: service role; cannot reach internet in a VPC: needs NAT; buildspec YAML errors; timeouts
  • CodeDeploy: agent not running or too old, instance profile cannot read the S3/GitHub revision, hook script failed (see scripts.log), health check failed, tag or ASG filter selects no instances, ELB deregistration delay too long
  • CodePipeline: not triggering = EventBridge rule/permissions; Deploy action access denied = pipeline role; artifact encryption/cross-account KMS problems
  • Beanstalk: deployment failed or unhealthy: check eb logs, environment health, instance profile permissions, port/health check path; use immutable to avoid partial deployments
ECS
  • CannotPullContainerError: no route to ECR (NAT or VPC endpoints), execution role missing ECR permissions, wrong image URI/tag
  • Task stops with exit code: application error, out of memory (container memory limit 137 = OOM kill), failed health check (ALB path, port, security group, grace period)
  • PENDING forever: no capacity/ENI/IPs in subnet, insufficient CPU/memory on EC2 container instances, placement constraints
  • Service does not scale: scaling policy/metric or max capacity; tasks fail to start due to the same reasons above
EC2, ELB, ASG, networking
  • SSH timeout: security group port 22, NACL, route table/IGW, public IP; Permission denied (publickey): wrong key or user (ec2-user, ubuntu); Connection refused: nothing listens
  • Instance status check fail: OS/software problem (reboot, console output); system status check fail: AWS hardware (stop/start)
  • ASG launch/terminate loops: health check grace period too short, app not ready, bad AMI or user data, ELB health check path wrong
  • No internet from private subnet: missing route to NAT gateway (and the NAT must be in a public subnet with an IGW route); security group/NACL stateless rules block return traffic (ephemeral ports 1024-65535)
  • NACLs are stateless and evaluated by rule number; security groups are stateful allow-only
  • High RDS connections from Lambda: use RDS Proxy; slow reads: read replicas, ElastiCache
Security and access
  • AccessDenied although policy allows: explicit deny elsewhere, SCP, permissions boundary, session policy, resource policy, missing KMS permission, condition (MFA, IP, VPC endpoint), wrong region/account; use IAM Policy Simulator, CloudTrail, decode-authorization-message
  • KMS ThrottlingException: enable S3 Bucket Keys, data key caching, backoff, request quota increase; AccessDeniedException on KMS: key policy/grant missing or key disabled/pending deletion
  • ExpiredToken: temporary credentials expired, refresh via role/SDK; InvalidClientTokenId or SignatureDoesNotMatch: wrong keys, wrong region/clock skew
  • Cognito: token expired (use refresh token), wrong audience/issuer, missing scopes; Identity Pool role lacks permissions

  • Latency by component: X-Ray service map
  • Who changed/deleted something: CloudTrail (CloudWatch does not know)
  • Is traffic reaching the VPC resource: VPC Flow Logs
  • Is the resource config different from the template: CloudFormation drift detection / AWS Config
  • Which permission is missing: IAM policy simulator, CloudTrail errorCode AccessDenied
  • Metrics not available by default (memory, disk): CloudWatch agent custom metrics
